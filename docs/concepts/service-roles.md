# Service Roles: Splitting the Control Plane from the Data Plane

One backend image, three deployment shapes, selected by `SERVICE_ROLE`:

| Role     | Serves                                                                 | Crons | Typical exposure           |
|----------|------------------------------------------------------------------------|-------|----------------------------|
| `all`    | Everything (default; identical to pre-split behavior)                  | yes   | Public (single container)  |
| `public` | Data plane: OAuth/OIDC, `/auth/*` login UI, member/tenant/SDK APIs     | no    | Public internet            |
| `admin`  | Control plane: `/admin/*` dashboard, super-admin/system APIs           | yes   | Internal ingress / IAP     |

`SERVICE_ROLE` is validated at boot: an invalid value **refuses to start**
(unlike `WEBHOOK_DELIVERY_MODE`, which forgivingly defaults). A typo that
silently became `all` would register admin controllers on an
internet-facing service.

## What the split guarantees

- The **public** service registers **no admin controllers** at all: the
  entire admin HTTP surface (super-admin APIs, system webhook CRUD, Pub/Sub
  admin, audit read/export, instance config write, license catalog admin)
  lives in `ControlPlaneModule`, which only loads for `admin | all`.
  Enforced by `app-module.roles.spec.ts`.
- `/admin/*` returns **404** on the public service; `/auth/*` returns 404 on
  the admin service (plane-gate middleware; no redirects, no SPA shell).
- Background jobs (outbox publisher, key rotation, MFA cleanup, license
  lifecycle) run **only** where `ScheduleModule` is registered: `admin | all`.
  Public replicas can scale horizontally without duplicating crons.
  Key *self-heal* on boot runs everywhere — it is idempotent and
  advisory-locked.

## Deployment constraints (read before splitting)

1. **`BASE_URL` is ALWAYS the public data-plane URL** on every service.
   OAuth issuer, JWKS URLs, email links, and admin-token issuers all derive
   from it — even when generated by admin-plane code. `ADMIN_BASE_URL` exists
   only to add the dashboard origin to the CORS allow-list.
2. **Admin sessions**: admin auth cookies are first-party cookies set by
   whichever host serves `/admin`. The supported topology is the dashboard
   served same-origin by the admin service (optionally behind IAP / an
   internal LB). Hosting the dashboard on a third origin would require
   cross-site cookie work that is deliberately out of scope.
3. **Pair the split with `WEBHOOK_DELIVERY_MODE=broker`** (the compose
   profile and `deploy-gcp.sh --split` do this). The broker owns webhook
   delivery, retries, and failure tracking.
4. **Shared frontend bundle**: both UI surfaces ship in one React build, so
   admin UI *code* is present in the public bundle's chunks. All admin APIs
   are absent from the public service, so that code is inert. Splitting the
   frontend build is future work.
5. The **admin** service may transitively expose some public-plane API routes
   (module imports carry controllers in Nest). This is harmless behind
   internal ingress and deliberate: strictness is asymmetric in the direction
   that matters.

## Try it locally

```bash
docker compose --profile split up -d postgres migrate \
  authvital-public authvital-admin authvital-broker
# public:  http://localhost:8090   (/admin -> 404)
# admin:   http://localhost:8091   (/auth  -> 404)
# broker:  http://localhost:8100/health
```

## GCP

```bash
./scripts/deploy-gcp.sh --project my-proj --base-url https://auth.example.com \
  --split --admin-base-url https://authadmin.internal.example.com
```

Deploys `authvital` (public), `authvital-admin` (internal ingress,
min-instances 1 — it owns the crons), `authvital-broker` (internal, Pub/Sub
transport with `authvital-events-dlq` dead-lettering after 10 attempts).
